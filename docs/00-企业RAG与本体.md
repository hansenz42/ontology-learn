# 导论 · 企业 RAG 已经找到了文件，为什么还会答错？

一家媒体企业把节目资料接入了内部知识助手。编辑问：“哪里可以找到《河流来信》的片尾署名？”助手检索到发行记录，给出文件和时间码，编辑点开就能核对。第二天，编辑换了一个问题：“我们已发行的作品里，哪些由林青执导？”同一批资料，现在要支撑一份准确的作品清单。

## 从已有的知识助手出发

检索增强生成（RAG）让模型在回答前先检索材料。企业可以将文档拆成段落，用关键词和向量混合检索，再通过重排选取相关段落。部门、日期和文档状态等元数据可以用于过滤，权限决定当前员工可以检索哪些材料，引用则让员工能回到原文。判断一个答案为什么出错，可以先查看检索结果：正确片段有没有入选？标题、来源和版本是否随片段一起送给模型？[Azure AI Search 的 RAG 说明](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview) · [Azure Databricks 的 RAG 质量指南](https://learn.microsoft.com/en-us/azure/databricks/agents/tutorials/ai-cookbook/quality-rag-chain)

以下是用于推演的虚构材料。假设三条记录都在编辑的可见范围内，检索也已经找全。

| 来源 | 记录内容 |
| --- | --- |
| 《河流来信》发行版片尾 24:10 | 导演：林青 |
| 《城市回声》立项提案，第 2 页 | 拟邀林青执导 |
| 《城市回声》发行版片尾 46:20 | 导演：周明；访谈嘉宾：林青 |

就这两部作品而言，答案只有《河流来信》，依据是发行版片尾 24:10。把《城市回声》也列进去，仍能引用一段含有“林青”和“执导”的原文。错在把计划当成了发行事实。针对这一次问答，限定检索发行材料并核对署名就可以解决。若每次编目、检索和报表都要重新解释“执导”指哪种参与、以哪个版本为准，团队就有理由把这个判断写成可复用的模型。

## 本体能替企业保存哪些判断？

本体（ontology）把团队使用的概念、关系及其含义写成明确的约定。在这个例子里，“作品”关联“发行版本”，“署名参与”把人物、角色和版本连在一起，“拟邀”则记录提案中的意向。编目员可以据此录入数据，报表开发者和问答系统也可以按同一个含义查“执导”。这些约定构成本体；“林青在《河流来信》发行版署名为导演”是使用这套约定记录的一条事实。

| 业务动作 | 在案例里怎样做 |
| --- | --- |
| 采集 | 从片尾抽取候选署名，保留版本标识和时间码。从提案抽取拟邀记录，保留页码。 |
| 审核 | 编目员核对片尾，确认人物身份和角色。若只有提案，发行署名保留为待核实。 |
| 问答 | 在员工有权访问的记录中，按人物、发行版本和导演角色筛选作品，把匹配记录和原文位置交给 RAG 生成带引用的回答。 |
| 更正 | 若新发行版更改署名，给新版本登记证据，保留旧版记录；查询指定版本时仍能解释当时的结果。 |

这里的成本是持续维护概念、映射和证据。若任务只是定位一份文件，先改善索引、过滤和引用即可。若多个部门反复按同一关系出清单，且版本混用会影响业务决策，可以先为这一个问题建模，用同一组材料比较现有 RAG 与加入模型后的结果：是否漏掉《河流来信》，是否误收《城市回声》，引用是否真的支持发行署名。上述推演提供参考答案，效果还需要在企业自己的资料上测量。

## 进入建模教程

从这个案例中取最小的一步：暂时固定发行版本，只保留两条已确认的参与记录。先预测按姓名查询与按姓名加角色查询各会返回哪些作品，再运行[第一课《一个人可以有几个角色？》](01-从问题到模型.md)核对结果。业务负责人可以先读完推演，实施人员可以继续动手查询。后续章节将逐步补回版本、证据位置和审核状态。
