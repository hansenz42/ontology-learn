# 2.4 检索索引已经有结构，还缺什么？
第一章给每个片段保存了来源、版本和权限，这些都是结构。现在看一个更细的问题：什么数据能让程序明确判断“林青在这个版本担任什么角色”？

## 给两种记录各写一行
片段索引的一行可以是“片段 C；人物词林青；类型片尾；位置 46:20”。即使它还包含“导演”“嘉宾”和“周明”三个词，光看词集合也无法确定哪个人担任哪个角色。发行署名表的两行则明确配对：“C 的发行版｜周明｜导演”“C 的发行版｜林青｜访谈嘉宾”。后两行使用了一项共同约定：一条署名连接特定版本、人物与角色。

这份约定可以实现在业务表，也可以表示成图，再供 RAG 查询。检索索引若显式保存这些关系，同样能够使用它们。技术选择取决于关系复用、查询和维护的需求。单看系统是否使用向量库，无法判断它有没有领域模型。

## 交付第二章的失败样例表
写三行并标出负责修复的环节。A 未进入索引，补齐解析与索引；B 进入上下文却被当作发行署名，明确关系语义并保留“拟邀”；两份来源对同一版本给出冲突署名，提交证据与审核决定。各行都写明修复后该重跑哪一道问题。第三章将选取第二行做手工推演。

## 思考
若馆藏只有几十个文件，编辑只想找出 A 的原文，你会立刻设计完整关系模型吗？说明你期望这个模型额外回答什么。

**自查。** 参考判断：先试文档定位。若另一个部门还要按角色出清单、按版本复核，并反复遇到同样歧义，再给共享关系定义写下一个可验证的使用理由。

## Q&A
**已有业务表还需要谈本体吗？** 可以先审查字段的业务定义。当“作者”在不同表中分别指撰稿、导演或任一参与人时，需要显式说明含义；有些旧概念可以直接复用。
