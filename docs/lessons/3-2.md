# 3.2 什么是领域本体？
编辑和报表开发者都用“导演”一词，却可能指人物的一般职业、一次实际参与，或某个版本上的署名。把大家准备共同采用的概念、关系及其含义写清，并使这些约定可以被检查，这就是本课建立领域本体的起点。

## 从概念走到一条实例
给“人物”写一句定义，给“发行版本”写一句定义，再给“署名参与”规定三个端点：一个人物、一个角色、一个发行版本。林青在《河流来信》的发行版上署名导演，是按这些约定描述的一条实例。把领域本体、实例和支持实例的证据一起用于查询，就有了这套小型知识库的核心。

角色只在具体参与中取值。林青可以在另一作品里担任嘉宾，人物身份可以稳定沿用。同样，剪辑活动发生在一段时间里，它产出一个可持续引用的版本。把活动和产物区分开，就可以分别问“何时剪辑”和“查询哪个版本”。

## 用反例检查定义
试用“导演是一个人物标签”来回答作品清单。只要人物有这个标签，她参与的每部作品都可能被误收。再用“角色属于一次署名参与”重答，程序就有了筛选的位置。这说明建模的价值出现在哪里：它迫使团队明确一项容易被省略、却影响答案的区别。后续可以用 RDF/OWL 写出更正式的模型；本节只需先验证区别有没有业务意义。

## 思考
把“拟邀”和“发行署名”都叫“参与”，再加一列记录类型，能否答对两道题？指出查询必须检查哪个字段，以及空值时该怎么处理。

**自查。** 参考判断：这种设计可以成立，但查询必须限制记录类型和角色，并处理缺少类型的记录。给出一条没有类型的输入，看你的规则会将它标为未知还是误收。

## Q&A
**每次遇到一个新词都要新建概念吗？** 先看它是否改变实例所属的范围或关系。名字不同但含义相同，可以保留为别名；同名但判断条件不同，则值得分开讨论。
